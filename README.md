# Telegram Event Bot

Мэй Мэй ведёт задачи и расписание через свободный русский текст. Она сама выбирает tools, составляет списки, напоминания и ответы. Приложение хранит данные, проверяет условия операций и доставляет готовый текст.

Характер задан в `src/agent/meimeiVoice.ts`: спокойная, уверенная и прагматичная Мэй Мэй, общающаяся на равных. Она оценивает пользу, цену, время и компетентность; меркантильность проявляется по делу. Речь короткая, без церемониальных обращений и ролевого театра. Один характер используется для диалогов, списков и фоновых напоминаний. Старые предпочтения господских обращений больше не применяются.

## Архитектура

```text
Telegram updates                       MySQL: наступившие задания
   │                                              │
   ├── текст → история                            ▼
   └── текст + контекст → BotBrain ←─────────── Worker
                              │
                              ▼
                    общий AgentRuntime
                              │
                    OpenAI Responses API
                              │ tool calls
                              ▼
                    ToolRegistry / ToolRuntime
                       │                │
                       ▼                ▼
                 Actions → MySQL    Telegram Adapter → Telegram
```

Оба процесса собирают один и тот же runtime через `createBrain`. Worker передаёт агенту тип задания и актуальные идентификаторы. Мэй Мэй читает нужные данные, применяет действия через tools и отправляет собственный текст через `send_message`. В фоне сервер восстанавливает владельца задания из БД: доступны прикладные tools в его области и текущем чате, включая создание новых расписаний. `record_readiness` привязан к фактическому ответу кнопки. Произвольное поручение можно завершить без сообщения через `finish_task`. История передаётся фоновому запуску как справочные данные. Отдельного генератора напоминаний и шаблонного запасного ответа нет.

LLM не получает прямой доступ к БД или выполнению кода. `ToolRegistry` содержит фиксированный набор tools, `ToolRuntime` проверяет их аргументы и результаты Zod-схемами. Задачи, заметки, расписания и память ограничены текущим чатом. Дневник настроения объединяет собственные записи пользователя из всех чатов.

## Запуск

Требования: Docker Compose либо Node.js 22 и MySQL 8.4.

1. Создайте конфигурацию:

   ```bash
   cp .env.example .env
   ```

2. Заполните как минимум:

   ```text
   TELEGRAM_BOT_TOKEN=...
   OPENAI_API_KEY=...
   MYSQL_PASSWORD=...
   MYSQL_ROOT_PASSWORD=...
   ```

3. Запустите локальное окружение:

   ```bash
   docker compose up --build
   ```

По умолчанию используется polling. При запуске он удаляет ранее зарегистрированный webhook, поэтому для local и production рекомендуется использовать разные Telegram bot tokens.

Healthcheck доступен на `GET http://localhost:3000/health`.

Compose запускает `app` и `mysql`. Контейнер `app` поднимает два процесса: бота и worker напоминаний. Worker получает задания из MySQL и запускает Мэй Мэй для напоминаний и ответов на кнопки, затем обновляет сводки переписки. Telegram updates принимает процесс бота.

При переходе с версии с отдельным сервисом `worker` пересоздайте окружение и удалите прежний контейнер воркера:

```bash
docker compose up -d --build --remove-orphans
```

### Production: один контейнер

Production-образ по умолчанию запускает и бота (`dist/app.js`), и worker (`dist/worker.js`). Для напоминаний отдельный контейнер или дополнительная команда не нужны:

```bash
docker build --target production -t telegram-event-bot .
docker run --name iraida --env-file .env --restart unless-stopped --stop-timeout 30 -p 3000:3000 telegram-event-bot
```

`MYSQL_HOST` должен указывать на доступную контейнеру MySQL. При нестандартном `PORT` измените проброс порта. Если площадка деплоя переопределяет команду образа на запуск одного `dist/app.js`, удалите это переопределение, чтобы использовался CMD образа.

`tini` передаёт сигналы менеджеру `concurrently`, который управляет обоими процессами. При завершении одного второй получает `SIGTERM`; при аварии контейнер завершается с ненулевым кодом, после чего его может перезапустить площадка. При остановке второго процесса менеджер даёт ему до 25 секунд на завершение перед `SIGKILL`, чтобы процессы успели закончить текущую операцию и снять блокировки. Незавершённое фоновое задание останется в MySQL для повторной попытки. Compose и пример `docker run` дают контейнеру 30 секунд; на площадке деплоя также задайте не меньше 30 секунд. Логи помечены `[bot]` и `[worker]`; начало работы воркера видно по `Notification worker started`.

### Webhook mode

Установите:

```text
TELEGRAM_MODE=webhook
TELEGRAM_WEBHOOK_URL=https://example.com/telegram/webhook
TELEGRAM_WEBHOOK_SECRET=<случайная секретная строка>
```

После запуска приложение зарегистрирует webhook и будет проверять заголовок `X-Telegram-Bot-Api-Secret-Token`. TLS/reverse proxy находятся за пределами этого проекта.

## Общение в чате

В личке Мэй Мэй обрабатывает весь текст и работает с личным списком задач. В группе весь полученный текст, включая подписи к сообщениям, сохраняется и передаётся модели вместе с контекстом. Сервер отмечает явные обращения: `@MeiMeiAssistantBot`, короткий псевдоним `@meimei`, «Мэй Мэй» или «Мэй» в начале сообщения, `/iraida`, `/ask`, команда для бота либо Reply на её сообщение. Настоящий username обработчик получает из Telegram автоматически; username и имя распознаются без учёта регистра. Имя внутри обычной фразы, цитаты или блока кода само по себе не считается явным обращением.

Продолжение разговора без повторного тега Мэй Мэй определяет сама по текущей реплике и недавней переписке. Например, после «Мэй, ты тут?» → «Тут. Что нужно?» можно написать «Покажи мне список дел». В контекст также передаются автор и текст сообщения, на которое сделан Reply. Если участники общаются между собой и связи с диалогом с ботом нет, Мэй Мэй выбирает `skip_reply`: завершает запуск без сообщения и без записи ответа в историю. Для лички, явных обращений и фоновых заданий этот tool недоступен. Таймера «активного диалога» нет; сообщения без тега тоже расходуют запрос к модели. Решение о том, кому адресована реплика, принимает модель по правилам в prompt.

Чтобы бот получал обычную переписку и обращения в группе, отключите Privacy Mode через BotFather (`/setprivacy` → `@MeiMeiAssistantBot` → Disable), затем удалите и заново добавьте его в группу. После этого отправьте `@MeiMeiAssistantBot привет`. Для проверки адресной команды используйте `/ask@MeiMeiAssistantBot привет`. `@meimei` остаётся локальным псевдонимом. Telegram описывает настройки получения сообщений в [документации Privacy Mode](https://core.telegram.org/bots/features#privacy-mode).

Обращение по имени — обычное сообщение для Telegram. Оно дойдёт до обработчика, если бот является администратором группы или Privacy Mode отключён.

Каждая группа имеет отдельный общий список задач. Любой её участник может просматривать и менять задачи, а также отвечать на кнопки готовности. Личные задачи и задачи других групп недоступны из этого чата. Групповой chat ID не становится личным адресом участника: для личных уведомлений пользователь должен сначала написать боту в личку.

## Память

Модель соответствует разделению [LangChain Memory](https://docs.langchain.com/oss/python/concepts/memory): краткосрочный контекст треда и долгосрочные записи в отдельных областях. Реализация — TypeScript и MySQL, без зависимости от LangChain.

У каждого личного или группового чата один тред. Telegram topics пока используют общий тред группы. Задачи привязаны к `chat_id`, переписка и сводка — к `thread_id`.

`ThreadMemory` хранит всю полученную текстовую переписку. В каждом запуске `MemoryContextBuilder` подаёт Мэй Мэй базовый prompt, профиль и правила доступной области, **готовую сохранённую сводку**, последние 50 сообщений и найденные по текущему запросу воспоминания. Воркер использует тот же сборщик. `CONVERSATION_HISTORY_LIMIT` задаёт размер недавнего контекста (50 по умолчанию), а не срок хранения. Старые сообщения доступны через `read_chat_messages`: `beforeId=null` начинает с последних, `nextBeforeId` ведёт к предыдущей странице.

`MemoryStore` хранит произвольное количество записей: `semantic` — устойчивые факты, `episodic` — полезный прошлый опыт, `procedural` — предпочтения и правила общения. Личность и обязанности Мэй Мэй остаются в базовом prompt. Личная область `user` доступна только в личке владельца; область `chat` — только в соответствующей группе, включая фоновые напоминания.

Мэй Мэй сама выделяет устойчивые сведения **из текущих обращений к ней**. Обычная переписка попадает в архив и сводку, но автоматически в отдельные воспоминания не превращается. `search_memory` ищет слова в ключе и содержимом внутри текущей области, возвращает до 10 записей и курсор следующей страницы. Это текстовый поиск MySQL, без векторной базы. `save_memory` сохраняет ключ, тип, содержание, источник и версию; источник и область задаёт сервер. Обновление требует прочитанную `expectedVersion`, создание — `null`; конфликт не перезаписывает свежую запись. `forget_memory` удаляет выбранную запись по ID и версии, исходная переписка и сводка сохраняются. Старый `save_user_preferences` доступен в личке и работает с записью `profile` в том же хранилище.

Сводка не генерируется в пути обычного ответа. После уведомлений воркер берёт максимум одну порцию: если за пределами последних 50 сообщений накопились ещё 50 необработанных, модель получает прежнюю сводку и следующие 50 старых сообщений. Она возвращает новую сводку до 4000 символов. Сводка и курсор сохраняются вместе; lease и версия защищают от конкурирующих воркеров. Ошибка оставляет прежнюю сводку и курсор, повтор — через 30 секунд. История не удаляется. При большой очереди сводка постепенно догоняет переписку; детали можно дочитать из архива. Актуальные сроки и статусы задач всегда берутся из tools, поскольку сводка отражает прошлое обсуждение.

## Задачи и список дел

- Из обращённого к Мэй Мэй сообщения или вставленного списка она создаёт от 1 до 100 задач одним `create_events`. Пакет валидируется и сохраняется атомарно. Задачи без даты принимаются сразу; неоднозначную указанную дату Мэй Мэй уточняет.
- На просьбу показать дела Мэй Мэй читает актуальные задачи из базы и отправляет собственный текст новым сообщением через `send_message`. Привязки к прежнему сообщению списка и фонового редактирования нет. Лимит последних 50 сообщений относится к контексту беседы, а не к доступности задач.
- Порядок задаётся сроком окончания (`dateTo`, иначе `dateFrom`), затем временем и ID. Просроченные остаются вверху до завершения или переноса, задачи без срока — в конце.
- `read_task_list` возвращает до 5 задач на странице, общее число задач и страниц. `page=null` начинает с первой страницы; другую можно прочитать по её номеру. Страница выбирается в запросе и не хранится как общее состояние чата. Мэй Мэй указывает авторов, названия, сроки и номер страницы, если выборка неполная.
- Выборки вроде «на неделю», «выполненные» или «напоминания» читаются через `search_schedule` / `search_notifications` и отправляются отдельным `send_message`.
- `complete_event` завершает задачу и отменяет ожидающие уведомления одной транзакцией. `delete_event` / `delete_events` мягко удаляют задачи, также отменяя уведомления. Завершённые и удалённые задачи исчезают из активного списка; строки остаются в БД.

Таблица `chat_lists`, оставшаяся от прежних версий, больше не читается и не обновляется приложением. Существующие задачи, напоминания и история сохраняются.

## Напоминания и готовность по умолчанию

После создания Мэй Мэй вызывает `configure_notifications` для новых задач. Пользователь может изменить это поведение явно.

| Задача | Напоминания | Вопрос готовности |
| --- | --- | --- |
| На 6 октября | 5 октября в 10:00 | 7 октября в 10:00 |
| С 5 по 11 октября включительно | 4 и 10 октября в 10:00 | 12 октября в 10:00 |
| Без срока | Нет стандартных таймеров | После назначения срока |

Время считается в зоне чата; по умолчанию это `Europe/Moscow` (МСК). Уже прошедшие моменты предварительных напоминаний пропускаются. Если срок уже прошёл при включении проверки готовности, вопрос назначается на ближайшие будущие 10:00. Совпадающие границы интервала не дают дубликатов.

Свои времена задаются режимом `custom`, отключение предварительных напоминаний — `off`, отключение вопроса готовности — `checkCompletion=false`. Просьба «без уведомлений» отключает оба вида. `create_notification` добавляет отдельное явное напоминание; `delete_notification` отменяет выбранное ожидающее уведомление. Поиск возвращает вид (`reminder` / `completion_check`) и источник (`manual` / `automatic`).

У задачи есть неизменяемый автор и отдельный получатель напоминаний. **По умолчанию получатель — автор**, в том числе у старых задач. По просьбе пользователя Мэй Мэй может назначить другого участника через `set_reminder_recipient`; `recipientTelegramUserId=null` возвращает адресацию автору. Смена получателя сохраняет ID задачи, даты, напоминания и кнопки готовности. Авторство не меняется. В общем списке Мэй Мэй указывает получателя отдельно, если он отличается от автора.

Получателем может быть только человек из текущего чата. `search_chat_members` ищет по имени или @username среди участников, известных по переписке и задачам этого чата, а также по Reply и именным упоминаниям текущего сообщения. Полного списка участников Telegram не предоставляет: если человек боту неизвестен, он может написать в группу либо пользователь может ответить на его сообщение через Reply. Профили из чужих чатов в поиск не попадают. В личке получателем остаётся владелец.

При явном назначении и перед отправкой сервер проверяет актуальное членство через [Telegram `getChatMember`](https://core.telegram.org/bots/api#getchatmember). Для гарантированной проверки других участников бот должен быть администратором группы. Боты, вышедшие и исключённые участники не допускаются; ограниченный участник допустим, только если `is_member=true`. Ошибка API не считается подтверждением членства. При невозможности проверки назначение отклоняется, а фоновая отправка остаётся в очереди для повтора; после смены получателя она может быть обработана сразу. Уже начатая генерация для прежнего получателя прерывается проверкой версии и блокировки перед отправкой.

В групповом напоминании или вопросе Мэй Мэй обращается к получателю. Она выбирает текст обращения, а `send_message` делает этот фрагмент кликабельным упоминанием доверенного Telegram ID. Личные предпочтения участников в общий фоновый ответ не передаются. В личке учитываются имя и предпочтения владельца.

После срока Мэй Мэй задаёт вопрос с кнопками **Да / Нет**:

- **Да**: агент вызывает `record_readiness`, задача становится завершённой и исчезает из активного списка.
- **Нет**: задача остаётся активной; Мэй Мэй спрашивает новую дату или интервал и просит ответить через Reply. Привязка ответа к задаче хранится в MySQL и переживает перезапуск.
- Ответить может любой участник текущей группы. Принимается первый ответ на текущую версию срока. Если никто не ответил, задача остаётся активной без ежедневных повторных вопросов.

При переносе `reschedule_event` атомарно сохраняет даты и заменяет ожидающие уведомления. Автоматические напоминания пересчитываются; отказ от уведомлений сохраняется. Для пользовательских ожидающих напоминаний агент выясняет новые времена. Неуказанные время и длительность интервала сохраняются, если пользователь не попросил их изменить. При фактическом переносе меняется `deadline_version`, поэтому прежние таймеры, кнопки и привязки Reply больше не относятся к новому сроку.

## Заметки

`notes` хранит название, полный текст, JSON-массив тегов, автора, чат, UTC-даты создания/изменения и версию. В личке доступны личные документы, в группе заметки общие: участники могут читать, дополнять и удалять их. Область доступа и автор определяются сервером; ID другой заметки не даёт доступа за пределами текущего чата.

- `create_note` создаёт документ с названием до 255 символов, текстом до 32000 символов и до 20 тегов по 64 символа. Текст сохраняет Markdown, переносы строк и чек-листы; пустой текст допустим. Теги нормализуются в нижний регистр, дубликаты удаляются.
- `search_notes` ищет фрагмент названия/текста и точный тег, `null` отключает фильтр. Возвращает метаданные и первые 300 символов текста с флагом `contentTruncated`; совпадение может находиться за пределами выдержки. Новые ID идут первыми, `nextBeforeId` задаёт следующую страницу. По умолчанию 20 записей, максимум 50.
- `read_note` читает полный документ с версией. Перед дополнением Мэй Мэй читает его целиком, затем передаёт полный текст, название и теги в `update_note`.
- `update_note` и `delete_note` требуют прочитанную `expectedVersion`. Конкурентная устаревшая правка возвращает `VERSION_CONFLICT` с актуальным документом, недоступная запись — `NOT_FOUND`. Автор и дата создания сохраняются при правках. Удаление физическое; история редакций не хранится, исходная переписка остаётся в архиве.

Все пять tools доступны также в фоновом поручении Scheduler с владельцем, заданным сервером. Инструкция может ссылаться на ID заметки, чтобы агент при запуске прочитал актуальный документ или дополнил его. Содержимое заметок передаётся как данные и само по себе не запускает действия.

## Настроение и Scheduler

`mood_entries` хранит владельца, целую оценку 1–10, необязательный комментарий, момент настроения в UTC, исходный часовой пояс и версию. Если время не указано, используется текущая минута; можно записать несколько оценок за день. В личке и группах доступны собственные записи из всего дневника. `create_mood`, `read_mood`, `search_moods`, `update_mood`, `delete_mood` создают, читают, исправляют и физически удаляют записи. Изменение/удаление проверяет прочитанную версию; исходная переписка сохраняется. Поиск поддерживает период, оценку, текст комментария и курсор; даты отображаются в зоне текущего чата. `get_mood_summary` считает количество, среднее, минимум, максимум и первую/последнюю записи за полуоткрытый период `[from, to)`. Причины и выводы Мэй Мэй формулирует по записям, которые может дочитать с пагинацией.

Scheduler принимает произвольные поручения агенту. Мэй Мэй сама выбирает содержание, время и регулярность, включая планирование из фонового запуска. Сводка настроения, обзор дел или вопрос пользователю хранятся как `kind=agent_task` и `payload={"instruction":"…"}`. Особого типа сводки, обязательного времени и ограничения на одну сводку в день нет.

- `schedule_once` сразу создаёт одно будущее уведомление; `schedule_id=NULL`.
- `create_schedule` сохраняет правило `daily` либо `weekly`, время, timezone и дни недели (`1` — понедельник, `7` — воскресенье). Воркер создаёт отдельные запуски.
- `search_schedules`, `update_schedule`, `delete_schedule` управляют собственными расписаниями текущего чата. Поиск возвращает ближайшее ожидающее уведомление и отдельный курсор генерации `nextUnqueuedAt`. Изменение требует прочитанную версию; удаление отключает расписание и сохраняет историю.
- `search_notifications` читает напоминания задач текущего чата и собственные `agent_task`, возвращает ID, версию и курсор страницы. `update_notification` меняет время/инструкцию разового pending-задания. `delete_notification` отменяет выбранный запуск; для изменения всей серии используется `update_schedule`.
- Необязательный `eventId` связывает поручение с активной задачей этого чата. Завершение, удаление или отключение напоминаний задачи останавливает связанные запуски и расписания. Перенос сохраняет правила повторения, отменяет старые запуски и пересчитывает будущие для новой версии срока.

Воркер перед отправкой пополняет очередь: у каждого включённого расписания один будущий запуск, независимо от повторных попыток текущего. Запуск и продвижение курсора фиксируются одной транзакцией; блокировки и уникальный ключ по расписанию, версии и моменту защищают от конкурентной генерации. Точечная отмена не откатывает курсор и не восстанавливается воркером. После простоя остаётся последний пропущенный запуск и ближайший будущий; старые неотправленные получают `skipped`. Календарные повторы сохраняют местное время при смене UTC-смещения: несуществующее время пропускается, повторяющийся час исполняется один раз, при первом вхождении.

Изменение или отключение серии отменяет её ожидающие запуски, включая уже взятый воркером. Версия и lease проверяются перед шагами, вызовами tools и отправкой. Поэтому изменение агентом собственного выполняющегося расписания останавливает старый запуск после изменения. Задание получает исходный `scheduledFor` и текущее время: задержка не должна смещать отчётный день сводки. Если сообщение не требуется, агент вызывает `finish_task`; задача получает `skipped` без отправки. Изменения памяти из фонового поручения помечаются источником `scheduled_task`.

## Agent runtime

Используется OpenAI Responses API, модель задаётся `OPENAI_MODEL` (`gpt-5.4-mini` по умолчанию). Один запрос может содержать несколько операций: например, найти и удалить старое расписание, создать новое, настроить уведомления и обновить список. После каждого tool результат возвращается модели, и она выбирает следующий шаг.

`parallel_tool_calls: false` означает один tool call в одном ответе модели; цикл допускает до `MAX_AGENT_STEPS` вызовов (по умолчанию 10). `tool_choice: required`, строгие схемы и обязательные ключи с `null` задают протокол. `OPENAI_MAX_OUTPUT_TOKENS` по умолчанию равен 16384, чтобы вместить пакет до 100 задач. Отправка через `send_message` завершает запуск, поэтому действия выполняются до общего итога. Для неадресованной реплики группы `skip_reply` завершает запуск без отправки текста.

В prompt заданы поведение Мэй Мэй, характер, правила уточнений и сценарии фоновых заданий. Решения о последовательности tools и весь видимый текст принимает модель. Данные чата и названия задач передаются как контекст; старое поручение в истории не становится новым заданием. Перед изменением существующей задачи агент перечитывает её через `search_events` или `read_event`.

При технической ошибке tools Мэй Мэй может сообщить подтверждённые результаты и невыполненную часть. Успешные операции разных tools автоматически не откатываются. Если сама модель недоступна, код пишет ошибку в лог; фоновые задания остаются для повтора. Успех тестов с заглушкой модели подтверждает только протокол, а не понимание естественного языка настоящей моделью.

## Хранение и worker

Основные таблицы:

| Таблица | Назначение |
| --- | --- |
| `chats` | Личный или групповой чат и его timezone |
| `threads` | Один тред на чат: сводка, курсор обработанных сообщений, версия и состояние фонового обновления |
| `events` | Задачи, автор, получатель напоминаний и его версия, nullable-даты, статус, версия срока и режим уведомлений |
| `mood_entries` | Личный дневник: оценка, комментарий, UTC-момент, timezone, версия |
| `notes` | Документы чата: название, текст, JSON-теги, автор, UTC-даты и версия |
| `schedules` | Владелец, чат, JSON-поручение, правило повторения, курсор и версия |
| `notifications` | Разовые запуски, включая `agent_task`: владелец, чат, kind, JSON, связь с расписанием, UTC-время, статус, lease, версия, поля задач и кнопок |
| `conversation_messages` | Архив треда с именами, message ID и Reply |
| `memories` | Факты, опыт, правила и профиль: область user/chat, ключ, источник и версия |

Миграции применяются при запуске. `008_thread_memory` переносит существующие календари в чаты, создаёт по треду на чат и переносит `user_preferences` в `memories/profile`. ID задач, сроки, часовые пояса, уведомления, сообщения списка и привязки кнопок сохраняются. История начинается с реально оставшихся сообщений: ранее удалённую переписку восстановить невозможно. Обратный откат требует отдельной миграции с сохранением памяти.

`009_reminder_recipient` добавляет необязательного получателя и версию назначения. `NULL` означает автора, поэтому существующие задачи продолжают адресоваться ему без пересоздания уведомлений.

`010_scheduler_moods` добавляет дневник и расписания, расширяет очередь и заполняет владельца/чат старых уведомлений из задач. ID уведомлений, сроки, статусы и Telegram message ID сохраняются. `schedule_id` и версия остаются колонками для поиска, отмены и проверки актуальности; содержание новых типов хранится в JSON. Обновляйте бот и воркер одной версией, остановив старые процессы перед миграцией. Проверку миграции выполняйте на отдельной тестовой базе; для отката данных нужна миграция вперёд.

`011_notes` создаёт отдельную таблицу заметок с внешними ключами на чат и автора и индексом для пагинации внутри чата. Прежние данные не изменяются; автоматический откат с удалением заметок не поддерживается.

После `007_agent_workflows` у существующих задач остаётся режим `legacy`: миграция не добавляет им новые уведомления. Такие задачи видны в списке; новые правила включаются при переносе или явной настройке. Новые задачи Мэй Мэй настраивает сразу после создания. Миграция не поддерживает автоматический откат к обязательной дате: для сохранения задач без срока потребуется отдельная миграция вперёд.

Worker забирает наступившие задания через `FOR UPDATE SKIP LOCKED`, назначает `lock_token` и запускает общий `BotBrain`. Перед очередным шагом и отправкой проверяются актуальность срока, получателя, статус и владение блокировкой. Для ответа **Да** допускается повторная доставка подтверждения уже завершённой задачи, если действие было применено до сбоя.

Настройки: `NOTIFICATION_POLL_INTERVAL_MS` (5000), `NOTIFICATION_BATCH_SIZE` (20), `NOTIFICATION_LOCK_TIMEOUT_MS` (60000). После порции уведомлений worker обрабатывает одну порцию сводки. Запрос сводки имеет отдельный таймаут до 20 секунд (также ограничен `OPENAI_TIMEOUT_MS`); блокировка живёт дольше таймаута. Неудачное задание получает задержку 30 секунд перед новой попыткой. Таймаут одного запроса модели ограничен минимумом из `OPENAI_TIMEOUT_MS`, 10 секунд и трети времени блокировки; для Telegram — минимумом из 10 секунд и трети времени блокировки. Автоматические повторы внутри клиента модели отключены.

`notifications.status` становится `sent` после успешного запуска с отправкой в Telegram; при ошибке снимается блокировка и сохраняется причина. Семантика доставки — at-least-once: при сбое между успешным Telegram API и фиксацией БД возможна повторная отправка. При остановке новые задания не берутся, незавершённые остаются для повторной обработки.

## Структура

```text
src/
├── app.ts                    # запуск бота, polling/webhook, lifecycle
├── worker.ts                 # диспетчер уведомлений и сводок
├── telegram/                 # grammY, обработчики, транспорт текста и кнопок
├── agent/                    # общий createBrain, BotBrain, runtime и prompt
│   └── tools/                # чтение, изменения, настройки и отправка
├── application/              # транзакции и правила хранения задач и памяти
├── db/                       # Kysely connection и migrations
├── config/
└── types/
```

REST API, автоматическое создание новых задач `events` на каждый повтор, массовое завершение, возврат завершённых задач в active, web UI и отдельные треды для Telegram topics пока отсутствуют. Регулярные поручения через Scheduler уже поддерживаются.
