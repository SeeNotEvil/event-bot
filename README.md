# Telegram Event Bot

Ираида Дедлайновна ведёт задачи и расписание через свободный русский текст. Она сама выбирает tools, составляет списки, напоминания и ответы. Приложение хранит данные, проверяет условия операций и доставляет готовый текст.

## Архитектура

```text
Telegram updates                       MySQL: наступившие задания
   │                                              │
   ├── обычные сообщения → история                 ▼
   └── обращение / Reply → BotBrain ←────────── Worker
                              │
                              ▼
                    общий AgentRuntime
                              │
                    OpenAI Responses API
                              │ tool calls
                              ▼
                    ToolRegistry / ToolRuntime
                       │                │
                       ▼                ▼
                 Actions → MySQL    Telegram Adapter → Telegram
```

Оба процесса собирают один и тот же runtime через `createBrain`. Worker передаёт агенту тип задания и актуальные идентификаторы. Ираида читает нужные данные, применяет действия через tools и отправляет собственный текст через `send_message` или `send_event_list`. В фоновом запуске доступны чтение, отправка и привязанный к кнопке `record_readiness`; обычные изменения задач и предпочтений требуют текущего поручения пользователя. История передаётся фоновому запуску как справочные данные. Отдельного генератора напоминаний и шаблонного запасного ответа нет.

LLM не получает прямой доступ к БД или выполнению кода. `ToolRegistry` содержит фиксированный набор tools, `ToolRuntime` проверяет их аргументы и результаты Zod-схемами. Все операции ограничены текущим чатом.

## Запуск

Требования: Docker Compose либо Node.js 22 и MySQL 8.4.

1. Создайте конфигурацию:

   ```bash
   cp .env.example .env
   ```

2. Заполните как минимум:

   ```text
   TELEGRAM_BOT_TOKEN=...
   OPENAI_API_KEY=...
   MYSQL_PASSWORD=...
   MYSQL_ROOT_PASSWORD=...
   ```

3. Запустите локальное окружение:

   ```bash
   docker compose up --build
   ```

По умолчанию используется polling. При запуске он удаляет ранее зарегистрированный webhook, поэтому для local и production рекомендуется использовать разные Telegram bot tokens.

Healthcheck доступен на `GET http://localhost:3000/health`.

Compose запускает `app` и `mysql`. Контейнер `app` поднимает два процесса: бота и worker напоминаний. Worker получает задания из MySQL и запускает Ираиду для напоминаний, ответов на кнопки и обновления списка. Telegram updates принимает процесс бота.

При переходе с версии с отдельным сервисом `worker` пересоздайте окружение и удалите прежний контейнер воркера:

```bash
docker compose up -d --build --remove-orphans
```

### Production: один контейнер

Production-образ по умолчанию запускает и бота (`dist/app.js`), и worker (`dist/worker.js`). Для напоминаний отдельный контейнер или дополнительная команда не нужны:

```bash
docker build --target production -t telegram-event-bot .
docker run --name iraida --env-file .env --restart unless-stopped --stop-timeout 30 -p 3000:3000 telegram-event-bot
```

`MYSQL_HOST` должен указывать на доступную контейнеру MySQL. При нестандартном `PORT` измените проброс порта. Если площадка деплоя переопределяет команду образа на запуск одного `dist/app.js`, удалите это переопределение, чтобы использовался CMD образа.

`tini` передаёт сигналы менеджеру `concurrently`, который управляет обоими процессами. При завершении одного второй получает `SIGTERM`; при аварии контейнер завершается с ненулевым кодом, после чего его может перезапустить площадка. При остановке второго процесса менеджер даёт ему до 25 секунд на завершение перед `SIGKILL`, чтобы процессы успели закончить текущую операцию и снять блокировки. Незавершённое фоновое задание останется в MySQL для повторной попытки. Compose и пример `docker run` дают контейнеру 30 секунд; на площадке деплоя также задайте не меньше 30 секунд. Логи помечены `[bot]` и `[worker]`; начало работы воркера видно по `Notification worker started`.

### Webhook mode

Установите:

```text
TELEGRAM_MODE=webhook
TELEGRAM_WEBHOOK_URL=https://example.com/telegram/webhook
TELEGRAM_WEBHOOK_SECRET=<случайная секретная строка>
```

После запуска приложение зарегистрирует webhook и будет проверять заголовок `X-Telegram-Bot-Api-Secret-Token`. TLS/reverse proxy находятся за пределами этого проекта.

## Общение в чате

В личке Ираида обрабатывает весь текст и работает с личным списком задач. В группе сохраняется обычная текстовая переписка, включая подписи к сообщениям. Модель запускается только при обращении: `@MeiMeiAssistantBot`, короткий псевдоним `@meimei`, `/iraida`, `/ask`, команда для бота либо Reply на его сообщение. Настоящий username обработчик получает из Telegram автоматически и распознаёт без учёта регистра. Имена и связи Reply сохраняются вместе с текстом; сама по себе запись обсуждения не создаёт задачи.

Чтобы бот получал обычную переписку и обращения в группе, отключите Privacy Mode через BotFather (`/setprivacy` → `@MeiMeiAssistantBot` → Disable), затем удалите и заново добавьте его в группу. После этого отправьте `@MeiMeiAssistantBot привет`. Для проверки адресной команды используйте `/ask@MeiMeiAssistantBot привет`. `@meimei` остаётся локальным псевдонимом. Telegram описывает настройки получения сообщений в [документации Privacy Mode](https://core.telegram.org/bots/features#privacy-mode).

Каждая группа имеет отдельный общий список задач. Любой её участник может просматривать и менять задачи, а также отвечать на кнопки готовности. Личные задачи и задачи других групп недоступны из этого чата. Групповой chat ID не становится личным адресом участника: для личных уведомлений пользователь должен сначала написать боту в личку.

## Память

Модель соответствует разделению [LangChain Memory](https://docs.langchain.com/oss/python/concepts/memory): краткосрочный контекст треда и долгосрочные записи в отдельных областях. Реализация — TypeScript и MySQL, без зависимости от LangChain.

У каждого личного или группового чата один тред. Telegram topics пока используют общий тред группы. Задачи и постоянный список привязаны к `chat_id`, переписка и сводка — к `thread_id`.

`ThreadMemory` хранит всю полученную текстовую переписку. В каждом запуске `MemoryContextBuilder` подаёт Ираиде базовый prompt, профиль и правила доступной области, **готовую сохранённую сводку**, последние 50 сообщений и найденные по текущему запросу воспоминания. Воркер использует тот же сборщик. `CONVERSATION_HISTORY_LIMIT` задаёт размер недавнего контекста (50 по умолчанию), а не срок хранения. Старые сообщения доступны через `read_chat_messages`: `beforeId=null` начинает с последних, `nextBeforeId` ведёт к предыдущей странице.

`MemoryStore` хранит произвольное количество записей: `semantic` — устойчивые факты, `episodic` — полезный прошлый опыт, `procedural` — предпочтения и правила общения. Личность и обязанности Ираиды остаются в базовом prompt. Личная область `user` доступна только в личке владельца; область `chat` — только в соответствующей группе, включая фоновые напоминания.

Ираида сама выделяет устойчивые сведения **из текущих обращений к ней**. Обычная переписка попадает в архив и сводку, но автоматически в отдельные воспоминания не превращается. `search_memory` ищет слова в ключе и содержимом внутри текущей области, возвращает до 10 записей и курсор следующей страницы. Это текстовый поиск MySQL, без векторной базы. `save_memory` сохраняет ключ, тип, содержание, источник и версию; источник и область задаёт сервер. Обновление требует прочитанную `expectedVersion`, создание — `null`; конфликт не перезаписывает свежую запись. `forget_memory` удаляет выбранную запись по ID и версии, исходная переписка и сводка сохраняются. Старый `save_user_preferences` доступен в личке и работает с записью `profile` в том же хранилище.

Сводка не генерируется в пути обычного ответа. После уведомлений и обновления списка воркер берёт максимум одну порцию: если за пределами последних 50 сообщений накопились ещё 50 необработанных, модель получает прежнюю сводку и следующие 50 старых сообщений. Она возвращает новую сводку до 4000 символов. Сводка и курсор сохраняются вместе; lease и версия защищают от конкурирующих воркеров. Ошибка оставляет прежнюю сводку и курсор, повтор — через 30 секунд. История не удаляется. При большой очереди сводка постепенно догоняет переписку; детали можно дочитать из архива. Актуальные сроки и статусы задач всегда берутся из tools, поскольку сводка отражает прошлое обсуждение.

## Задачи и постоянный список

- Из обращённого к Ираиде сообщения или вставленного списка она создаёт от 1 до 100 задач одним `create_events`. Пакет валидируется и сохраняется атомарно. Задачи без даты принимаются сразу; неоднозначную указанную дату Ираида уточняет.
- У чата одно сообщение с активным списком. После изменений оно обновляется: Ираида читает `read_task_list`, пишет полный текст страницы и вызывает `send_event_list`. Telegram Adapter не составляет пункты и не добавляет авторов или даты в текст.
- Порядок задаётся сроком окончания (`dateTo`, иначе `dateFrom`), затем временем и ID. Просроченные остаются вверху до завершения или переноса, задачи без срока — в конце.
- На странице до 5 задач. Кнопки переключают страницы того же сообщения. Ираида указывает авторов, названия, сроки и номер страницы. Удалённое сообщение списка создаётся заново при следующем обновлении.
- Выборки вроде «на неделю», «выполненные» или «напоминания» читаются через `search_schedule` / `search_notifications` и отправляются отдельным `send_message`. Они не заменяют постоянный активный список.
- `complete_event` завершает задачу и отменяет ожидающие уведомления одной транзакцией. `delete_event` / `delete_events` мягко удаляют задачи, также отменяя уведомления. Завершённые и удалённые задачи исчезают из активного списка; строки остаются в БД.

При изменении данных увеличивается версия списка. Worker подбирает неопубликованные версии; если изменения произошли во время отправки, новая версия остаётся в очереди. Блокировка публикации не позволяет двум процессам одновременно создавать начальное сообщение списка.

## Напоминания и готовность по умолчанию

После создания Ираида вызывает `configure_notifications` для новых задач. Пользователь может изменить это поведение явно.

| Задача | Напоминания | Вопрос готовности |
| --- | --- | --- |
| На 6 октября | 5 октября в 10:00 | 7 октября в 10:00 |
| С 5 по 11 октября включительно | 4 и 10 октября в 10:00 | 12 октября в 10:00 |
| Без срока | Нет стандартных таймеров | После назначения срока |

Время считается в зоне чата; по умолчанию это `Europe/Moscow` (МСК). Уже прошедшие моменты предварительных напоминаний пропускаются. Если срок уже прошёл при включении проверки готовности, вопрос назначается на ближайшие будущие 10:00. Совпадающие границы интервала не дают дубликатов.

Свои времена задаются режимом `custom`, отключение предварительных напоминаний — `off`, отключение вопроса готовности — `checkCompletion=false`. Просьба «без уведомлений» отключает оба вида. `create_notification` добавляет отдельное явное напоминание; `delete_notification` отменяет выбранное ожидающее уведомление. Поиск возвращает вид (`reminder` / `completion_check`) и источник (`manual` / `automatic`).

В групповом напоминании или вопросе Ираида обращается к автору задачи. Она выбирает текст обращения, а `send_message` делает этот фрагмент кликабельным упоминанием доверенного Telegram ID. Личные предпочтения автора в общий фоновый ответ не передаются. В личке учитываются имя и предпочтения владельца.

После срока Ираида задаёт вопрос с кнопками **Да / Нет**:

- **Да**: агент вызывает `record_readiness`, задача становится завершённой и исчезает из активного списка.
- **Нет**: задача остаётся активной; Ираида спрашивает новую дату или интервал и просит ответить через Reply. Привязка ответа к задаче хранится в MySQL и переживает перезапуск.
- Ответить может любой участник текущей группы. Принимается первый ответ на текущую версию срока. Если никто не ответил, задача остаётся активной без ежедневных повторных вопросов.

При переносе `reschedule_event` атомарно сохраняет даты и заменяет ожидающие уведомления. Автоматические напоминания пересчитываются; отказ от уведомлений сохраняется. Для пользовательских ожидающих напоминаний агент выясняет новые времена. Неуказанные время и длительность интервала сохраняются, если пользователь не попросил их изменить. При фактическом переносе меняется `deadline_version`, поэтому прежние таймеры, кнопки и привязки Reply больше не относятся к новому сроку.

## Agent runtime

Используется OpenAI Responses API, модель задаётся `OPENAI_MODEL` (`gpt-5.4-mini` по умолчанию). Один запрос может содержать несколько операций: например, найти и удалить старое расписание, создать новое, настроить уведомления и обновить список. После каждого tool результат возвращается модели, и она выбирает следующий шаг.

`parallel_tool_calls: false` означает один tool call в одном ответе модели; цикл допускает до `MAX_AGENT_STEPS` вызовов (по умолчанию 10). `tool_choice: required`, строгие схемы и обязательные ключи с `null` задают протокол. `OPENAI_MAX_OUTPUT_TOKENS` по умолчанию равен 16384, чтобы вместить пакет до 100 задач. Отправка через `send_message` / `send_event_list` завершает запуск, поэтому действия выполняются до общего итога.

В prompt заданы поведение Ираиды, характер, правила уточнений и сценарии фоновых заданий. Решения о последовательности tools и весь видимый текст принимает модель. Данные чата и названия задач передаются как контекст; старое поручение в истории не становится новым заданием. Перед изменением существующей задачи агент перечитывает её через `search_events` или `read_event`.

При технической ошибке tools Ираида может сообщить подтверждённые результаты и невыполненную часть. Успешные операции разных tools автоматически не откатываются. Если сама модель недоступна, код пишет ошибку в лог; фоновые задания остаются для повтора. Успех тестов с заглушкой модели подтверждает только протокол, а не понимание естественного языка настоящей моделью.

## Хранение и worker

Основные таблицы:

| Таблица | Назначение |
| --- | --- |
| `chats` | Личный или групповой чат и его timezone |
| `threads` | Один тред на чат: сводка, курсор обработанных сообщений, версия и состояние фонового обновления |
| `events` | Задачи, автор, nullable-даты, статус, версия срока и режим уведомлений |
| `notifications` | Напоминания, вопросы готовности и задания на обработку ответов; UTC-время, статус, блокировка, версия срока, Telegram message ID |
| `chat_lists` | Message ID общего списка, текущая и опубликованная версии, страница, блокировка публикации |
| `conversation_messages` | Архив треда с именами, message ID и Reply |
| `memories` | Факты, опыт, правила и профиль: область user/chat, ключ, источник и версия |

Миграции применяются при запуске. `008_thread_memory` переносит существующие календари в чаты, создаёт по треду на чат и переносит `user_preferences` в `memories/profile`. ID задач, сроки, часовые пояса, уведомления, сообщения списка и привязки кнопок сохраняются. История начинается с реально оставшихся сообщений: ранее удалённую переписку восстановить невозможно. Обратный откат требует отдельной миграции с сохранением памяти.

После `007_agent_workflows` у существующих задач остаётся режим `legacy`: миграция не добавляет им новые уведомления. Такие задачи видны в списке; новые правила включаются при переносе или явной настройке. Новые задачи Ираида настраивает сразу после создания. Миграция не поддерживает автоматический откат к обязательной дате: для сохранения задач без срока потребуется отдельная миграция вперёд.

Worker забирает наступившие задания через `FOR UPDATE SKIP LOCKED`, назначает `lock_token` и запускает общий `BotBrain`. Перед очередным шагом и отправкой проверяются актуальность срока, статус и владение блокировкой. Для ответа **Да** допускается повторная доставка подтверждения уже завершённой задачи, если действие было применено до сбоя.

Настройки: `NOTIFICATION_POLL_INTERVAL_MS` (5000), `NOTIFICATION_BATCH_SIZE` (20), `NOTIFICATION_LOCK_TIMEOUT_MS` (60000). После порции уведомлений worker обрабатывает изменение списка, затем одну порцию сводки. Запрос сводки имеет отдельный таймаут до 20 секунд (также ограничен `OPENAI_TIMEOUT_MS`); блокировка живёт дольше таймаута. Неудачное задание получает задержку 30 секунд перед новой попыткой. Таймаут одного запроса модели ограничен минимумом из `OPENAI_TIMEOUT_MS`, 10 секунд и трети времени блокировки; для Telegram — минимумом из 10 секунд и трети времени блокировки. Автоматические повторы внутри клиента модели отключены.

`notifications.status` становится `sent` после успешного запуска с отправкой в Telegram; при ошибке снимается блокировка и сохраняется причина. Семантика доставки — at-least-once: при сбое между успешным Telegram API и фиксацией БД возможна повторная отправка. При остановке новые задания не берутся, незавершённые остаются для повторной обработки.

## Структура

```text
src/
├── app.ts                    # запуск бота, polling/webhook, lifecycle
├── worker.ts                 # диспетчер уведомлений, списка и сводок
├── telegram/                 # grammY, обработчики, транспорт текста и кнопок
├── agent/                    # общий createBrain, BotBrain, runtime и prompt
│   └── tools/                # чтение, изменения, настройки и отправка
├── application/              # транзакции и правила хранения задач и памяти
├── db/                       # Kysely connection и migrations
├── config/
└── types/
```

REST API, повторяющиеся события, массовое завершение, возврат завершённых задач в active, web UI и отдельные треды для Telegram topics пока отсутствуют.
